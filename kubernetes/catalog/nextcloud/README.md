# Advanced Storage — NAS Runbook

This runbook accompanies [`InfraWeaver-platform/plans/advanced-storage.md`](../../InfraWeaver-platform/plans/advanced-storage.md)
and covers the **manual, one-time** steps needed on the NAS side so the
in-cluster manifests can materialise.

The console flow (Storage → NAS & external → Mount to workload) automates
everything **inside** the cluster: generating StorageClass + PVC manifests,
patching Deployment `volumeMounts`, committing to git. The NAS itself is not
managed by GitOps — those steps live here.

## 1. Naming convention (generic)

Every NAS-backed workload follows the same shape, so future apps slot in
without inventing new patterns:

| Concern | Convention |
| --- | --- |
| K8s secret with SMB creds | `nas-<share>-<ro\|rw>` |
| StorageClass | `<backend>-<user>-<share>-<ro\|rw>`, e.g. `smb-jellyfin-media-ro` |
| PVC name | `nas-<user>-<share>` (or `nas-<deployment>-<share>-<access>` for app-centric mounts) |
| OpenBao path | `secret/platform/nas/<share>-<ro\|rw>` |
| NAS service account | `svc-<workload>` on the NAS, ACL scoped to one share only |

If a share needs both RO and RW access from different workloads, create
**two** service accounts on the NAS (one per access mode), and store both
credentials in OpenBao under `.../media-ro` and `.../media-rw`.

## 2. Adding a new NAS provider

The console reads providers from a registry (see
`apps/infraweaver-console/src/lib/nas/providers.ts`). Built-in providers
(Synology, TrueNAS) are enabled when their host env is set. Extra providers
are declared via the `NAS_PROVIDERS_JSON` env var on the console deployment:

```json
[
  {
    "id": "synology-office",
    "name": "Office Synology",
    "host": "10.30.0.10",
    "port": 5001,
    "protocol": "https",
    "kind": "synology",
    "backends": ["smb"],
    "enabledEnv": "SYNOLOGY_OFFICE_PASSWORD"
  }
]
```

Once registered, the provider shows up in every UI/API automatically
(providers list, share picker, mounts table, breakdown pie).

## 3. One-time NAS-side prep (media example)

Applies to the Jellyfin (RO) + Nextcloud (RW) worked example.

### Synology (or TrueNAS)

1. Create a dedicated shared folder / dataset: `media`. Do **not** reuse an
   existing multi-purpose share — the share root is the security boundary.
2. Create two SMB service accounts:
   - `svc-jellyfin` → **read-only** ACL on `media`, no access to any other
     share. Disable interactive login.
   - `svc-nextcloud` → **read-write** ACL on `media`, no access to any other
     share. Disable interactive login.
3. Confirm SMB (min v3, disable v1) is enabled on the share.

### OpenBao

Store both credentials so ExternalSecrets can pull them into the consuming
namespaces. The naming pattern is `secret/platform/nas/<provider>-<share>-<access>`
so multiple NAS units can coexist without collisions.

```sh
# Jellyfin RO (Synology — legacy simple name, kept for backwards compatibility)
bao kv put secret/platform/nas/media-ro \
  username=svc-jellyfin \
  password='<generated>'

# Per-provider RW paths consumed by Nextcloud
bao kv put secret/platform/nas/synology-media-rw \
  username=svc-nextcloud-synology \
  password='<generated>' \
  host=10.1.0.21 \
  share=media

bao kv put secret/platform/nas/truenas-media-rw \
  username=svc-nextcloud-truenas \
  password='<generated>' \
  host=10.1.0.22 \
  share=media
```

And the Nextcloud app + DB + OIDC secrets:

```sh
bao kv put secret/platform/nextcloud \
  admin_user=admin \
  admin_password='<generated>' \
  db_user=nextcloud \
  db_password='<generated>' \
  db_name=nextcloud \
  db_host=postgresql-nextcloud

# OIDC — client_secret is auto-generated by Authentik when the
# "Nextcloud Provider" oauth2provider is created (blueprint-apps.yaml).
# Read it once via the Authentik admin API or UI.
bao kv put secret/platform/nextcloud-oidc \
  client_id=nextcloud \
  client_secret='<from Authentik>' \
  discovery_url='https://auth.<BASE_DOMAIN>/application/o/nextcloud/.well-known/openid-configuration'
```

## 4. Authentik + Nextcloud SSO (fully automatic)

Once `blueprint-apps.yaml` and `blueprint-access-control.yaml` are applied by
Authentik and the `secret/platform/nextcloud-oidc` OpenBao entry exists, the
Nextcloud post-install Job configures everything on its own:

1. Enables the `user_oidc` app.
2. Registers Authentik as the SSO provider with:
   - `client_id`, `client_secret`, `discovery_url` from the ExternalSecret
   - claim mapping `preferred_username → uid`, `name → display`, `email → email`
   - **group claim `nc_groups`** (see the Nextcloud Groups Scope in
     `blueprint-apps.yaml`) so every Authentik group becomes a Nextcloud group
     of the same name
   - `--check-bearer=0` so WebDAV / OAuth clients still authenticate natively

Access to Nextcloud is gated by `policy-nc-users` in
`blueprint-access-control.yaml` — the user must be in `platform-admins`,
`nc-users`, `nc-media-ro`, `nc-media-rw`, `nc-truenas`, or `nc-synology`.

## 5. Per-folder RBAC (InfraWeaver ↔ Nextcloud, one source of truth)

Every NAS folder is gated by the same group name in **three** places, so the
authorization model is uniform across CSI mounts and Nextcloud UI:

| Layer | How the group is checked |
| --- | --- |
| InfraWeaver console — `POST /api/nas/assign` and `/mount-workload` | `NAS_FOLDER_ACL_JSON` (see `src/lib/nas/folder-acl.ts`) |
| Nextcloud External Storage mount visibility | `occ files_external:applicable --add-group <name>` (run by the post-install Job) |
| Authentik app access to Nextcloud itself | `policy-nc-users` binding (in `blueprint-access-control.yaml`) |

Example console env:

```
NAS_FOLDER_ACL_JSON='[
  { "provider":"synology","share":"media",
    "allow":{"readonly":["nc-media-ro","platform-users"],"readwrite":["nc-media-rw"]}},
  { "provider":"truenas","share":"media",
    "allow":{"readonly":["nc-media-ro"],"readwrite":["nc-media-rw","nc-truenas"]}},
  { "provider":"synology","share":"finance","subfolder_prefix":"reports/",
    "allow":{"readonly":["finance-viewers"],"readwrite":["finance-editors"]}}
]'
```

Rules:
- Callers holding the `*` (owner) permission bypass folder ACL.
- Shares with **no** rule stay open (opt-in tightening); once a share has any
  rule, unlisted subfolders inside it are denied.
- `readwrite` grants imply `readonly`.
- Use `@user:<name>` in an `allow` list to grant a specific user without
  creating a group.

To onboard a new folder:
1. Create the Authentik group (edit `blueprint-access-control.yaml`).
2. Add an ACL entry to the console's `NAS_FOLDER_ACL_JSON`.
3. If the folder should also appear in Nextcloud, add an `add_smb_mount` call
   to `configmap-postinstall.yaml` referencing the same group name.
4. Assign the group to users in Authentik. All three enforcement points pick
   up the change on the next login / next `occ` run.

## 6. Verifying the RO invariant (Jellyfin cannot write)

After the Jellyfin pod rolls with the new NAS mount:

```sh
kubectl -n jellyfin exec deploy/jellyfin -- sh -c 'touch /data/canary && echo OK || echo BLOCKED'
# Expected: BLOCKED (with "Read-only file system")
```

If this prints `OK`, one of the three layers is broken:
- Layer A: the `svc-jellyfin` NAS account is not RO.
- Layer B: the StorageClass references the RW secret.
- Layer C: the deployment `volumeMount` is missing `readOnly: true`.

## 7. Adding NFS support later

`nfs.csi.k8s.io` is already understood by the manifest generator
(`backend: "nfs"`). To enable it in the cluster:

1. Install `csi-driver-nfs` (mirror the existing `csi-driver-smb` layout in
   `kubernetes/core/`).
2. Add `"nfs"` to the `backends` array of the relevant provider in
   `NAS_PROVIDERS_JSON`, or in `providers.ts`.
3. The console will start offering NFS as a backend option in the mount
   flow; no other code changes needed.
